# Анализ Privacy by Design: As-Is → To-Be

## 1. Сводка As-Is

| Принцип PbD | As-Is | Риск |
|-------------|-------|------|
| **Проактивность, не реактивность** | Защита не заложена; общий диск, нет шифрования | Утечка до внедрения контролей |
| **Конфиденциальность по умолчанию** | Максимальный доступ по AD; PII в именах файлов | Любой сотрудник видит все данные |
| **Встроенная конфиденциальность** | Excel/1С без privacy-контролов | Каждый новый сервис проектируется «с нуля» |
| **Полнота функций** | Нет удаления по запросу, нет согласий | Нарушение прав субъекта ПДн |
| **Защита на протяжении жизненного цикла** | Нет retention, нет lineage | «Вечные» копии в Excel и бэкапах |
| **Прозрачность** | Нет аудита | Невозможно доказать compliance |
| **Уважение к частной жизни пользователя** | Сбор всех полей анкеты | Избыточная обработка ПДн |

## 2. Механизмы управления рисками (до реализации)

Механизмы проектируются **до** разработки прикладных сервисов и встраиваются как обязательные зависимости.

### 2.1. Слой управления конфиденциальностью (Privacy Control Plane)

| Блок | Механизм | Риск, который предотвращает |
|------|----------|----------------------------|
| **Платформа тегирования данных** | Автоклассификация + ручная валидация тегов (`pii`, `pii.sensitive`) | Неконтролируемая обработка чувствительных данных |
| **Движок политик (OPA)** | Policy-as-code: ABAC по тегам и ролям | BOLA/IDOR, доступ врача к чужим картам |
| **Служба согласий** | Реестр целей обработки, сроков, отзывов | Обработка без правового основания (152-ФЗ) |
| **KMS / Vault** | Ключи шифрования по тегам `policy.encrypt` | Утечка at rest при компрометации диска |
| **Privacy API Gateway** | Фильтрация полей API по тегам, rate limiting | Утечка через API, избыточные поля в ответах |
| **Служба аудита** | Immutable audit log, алерты на аномалии | Незамеченный инсайдерский доступ |
| **CI/CD Privacy Gate** | Semgrep + OPA Conftest на тегированные поля | PII в логах и коде после релиза |

### 2.2. Встроенные практики в прикладные системы

| Система | PbD-механизм |
|---------|--------------|
| CRM / Портал пациента | Data Minimization: сбор только нужных полей; псевдонимизация ID |
| МИС (мед. карты) | Шифрование `pii.sensitive`, ABAC «врач → свои пациенты» |
| Платёжный шлюз | Токенизация платёжных данных; минимизация ПДн в чеке |
| Интеграция с лабораторией | API-контракты скрывают чувствительные поля; mTLS |
| Портал ресепшена | Маскирование ФИО в списках; аудит каждого просмотра |

### 2.3. Слой аналитики с Privacy by Design

Отдельный контур, **изолированный** от операционных ПДн:

```
Операционные БД → ETL → [Зона Raw: шифрование] → Псевдонимизация/обезличивание → [Зона Analytics] → ClickHouse → BI/ML
                              ↑                              ↑
                        OpenMetadata                   Только теги int/aggregated
                        Data Lineage                   Запрет pii.sensitive
```

| Компонент | Назначение | PbD-принцип |
|-----------|------------|-------------|
| **Data Lake (Raw)** | Приём данных с lineage | Защита на протяжении жизненного цикла |
| **Anonymization Pipeline** | k-anonymity, псевдонимизация, агрегация | Data Minimization для аналитики |
| **ClickHouse (Analytics)** | Только обезличенные витрины | Конфиденциальность по умолчанию |
| **OpenMetadata** | Каталог, lineage, блокировка promoted datasets с `pii` | Прозрачность |
| **Jupyter / ML Workspace** | Доступ только к anonymized zone | Уважение к частной жизни |

**Правило:** бизнес-аналитик **никогда** не получает прямой доступ к операционным Excel/БД с PII — только к витринам с тегом `policy.anonymize`.

## 3. Новые блоки целевой архитектуры (C4 Context)

### Бизнес-системы (из требований To-Be)

1. Портал пациента (web + mobile)
2. Портал ресепшена
3. CRM
4. МИС — медицинские карты
5. Сервис записи на приём
6. Платёжный шлюз
7. Интеграция с лабораторией

### Блоки Privacy by Design (сквозные)

8. **Privacy API Gateway** — единая точка входа, фильтрация по тегам
9. **Платформа тегирования и каталога данных** (OpenMetadata)
10. **Движок политик конфиденциальности** (OPA)
11. **Служба управления согласиями**
12. **Служба ключей и шифрования** (Vault)
13. **Служба аудита и мониторинга** (Elastic + Victoria Metrics)

### Слой аналитики

14. **Платформа аналитики с защитой конфиденциальности** — Data Lake + Anonymization Pipeline + ClickHouse + BI

### Внешние системы (сохраняются/интегрируются)

- Лаборатория анализов
- 1С:Бухгалтерия, 1С:Торговля и склад
- ККМ / эквайринг
- Active Directory
- Провайдер SMS/голосовых уведомлений

## 4. Матрица риск → механизм

| Риск | Механизм To-Be | Блок архитектуры |
|------|----------------|------------------|
| Утечка через API | Field-level filtering, BOLA-защита | Privacy API Gateway + OPA |
| Доступ к чужим данным | ABAC по patient_id + role | OPA |
| PII в аналитике | Обязательное обезличивание | Anonymization Pipeline |
| Утечка at rest | AES-256, ключи в Vault | KMS + теги `policy.encrypt` |
| Обработка без согласия | Consent check перед write | Служба согласий |
| Незамеченная утечка | Аудит + алерты | Elastic, Victoria Metrics |
| PII в релизе | CI privacy gate | Semgrep + OPA Conftest |
| Невозможность удаления | Data Lineage + delete workflow | OpenMetadata + CRM |

## 5. Этапы внедрения механизмов

| Этап | Срок | Механизмы |
|------|------|-----------|
| **MVP** | ~2 мес. | Gateway, OPA (базовый RBAC), теги `pii`, аудит записей |
| **Расширение** | 3–6 мес. | Vault, Consent Service, ABAC, лаборатория через API |
| **Полная автоматизация** | ~1 год | CI privacy gate, полный analytics layer, ML на anonymized data |
