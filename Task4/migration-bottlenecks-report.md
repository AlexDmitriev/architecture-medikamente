# Отчёт: оценка узких мест при миграции

## 1. Контекст миграции

Компания «Медикаменте» переходит от ручных процессов, Excel-файлов, сканов и 1С в файловом режиме к целевой архитектуре с порталами, CRM, платёжным шлюзом, интеграцией с лабораторией, мобильным приложением и аналитическим слоем.

Ключевой риск миграции — не только техническая замена монолитных и файловых решений на микросервисную архитектуру, но и перенос бизнес-критичных процессов без деградации производительности, доступности и качества данных.

## 2. Процессы и компоненты, затрагиваемые миграцией

| Область | As-Is | To-Be | Потенциальное узкое место |
|---------|-------|-------|---------------------------|
| Запись пациента | Excel-журналы на общем диске | Портал пациента, портал ресепшена, сервис записи | Конкурентная запись в один слот, рост нагрузки x5, синхронизация с уведомлениями |
| Учёт пациентов | Excel `Patients`, папки `Pacient-FIO-BD` | CRM, единый patient profile | Очистка дублей, качество миграции ПДн, сопоставление файлов с пациентами |
| Медицинские карты | PDF/JPG, сканы на файловом сервере | МИС, защищённое файловое/объектное хранилище | Медленная загрузка файлов, OCR/индексация, миграция больших объёмов |
| Анализы | Excel-реестры лаборатории | API-интеграция с лабораторией | Задержки API, несовместимость контрактов, идемпотентность результатов |
| Оплата | ККМ + 1С + Excel-дубли | Платёжный шлюз, интеграция с 1С/ККМ | Двойное списание, задержки фискализации, синхронизация статусов |
| Бухгалтерия и склад | 1С в файловом режиме | Интеграция с сервисами / клиент-серверный контур 1С | Блокировки 1С, медленный обмен, зависимость от legacy |
| Инфраструктура | Один физический Windows Server | Kubernetes/Postgres/ClickHouse/Elastic/Victoria Metrics | Недостаток ресурсов, единая точка отказа, сетевые задержки |
| Аналитика | Jupyter по Excel | Data Lake, обезличивание, ClickHouse, BI/ML | ETL перегружает операционные БД, raw PII попадает в витрины |
| Безопасность | Доменная аутентификация, нет аудита | RBAC/ABAC, аудит, тегирование, шифрование | Policy engine/API Gateway становятся критическим путём |

## 4. Основные проблемные зоны

### 4.1. Инфраструктура

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| Один физический сервер в офисе | Вся текущая система зависит от одного узла | Отказ сервера останавливает запись, 1С, файлы, почту |
| Нет выделенных контуров app/data/analytics | Аналитика и пользовательские сервисы конкурируют за ресурсы | Просадка производительности CRM/МИС при ETL |
| Нет оценки ёмкости под x5 рост | Рост клиентов, файлов и сотрудников не рассчитан | Недостаток CPU/RAM/IOPS, медленные запросы |
| Локальная сеть не готова к новым филиалам | Филиалы увеличат latency и нагрузку на VPN/WAN | Нестабильная работа порталов и 1С |

### 4.2. Данные и хранилища

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| Excel и сканы без единой модели данных | Нет нормализованных сущностей и ключей | Долгая миграция, дубли, ошибки сопоставления |
| PII в именах файлов и папок | Метаданные сами являются данными | Нельзя безопасно мигрировать без предварительной очистки |
| Большие PDF/JPG | Файлы тяжёлые, плохо индексируются | Долгая загрузка, медленный поиск, рост storage |
| Нет Data Lineage | Неясно, где существуют копии данных | Риск потери или несогласованности при миграции |

### 4.3. Интеграции

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| 1С в файловом режиме | Файловая 1С плохо масштабируется и блокируется | Задержки платежей и бухгалтерских операций |
| ККМ через TCP/OLE | Legacy-протоколы трудно сделать отказоустойчивыми | Ошибки фискализации, зависшие платежи |
| Лаборатория пока без API | Контракты, SLA и идемпотентность не определены | Потеря/дублирование результатов анализов |
| Outlook/Exchange вне потоков | Коммуникации с ПДн не формализованы | Неконтролируемые уведомления и ручные обходные процессы |

### 4.4. Архитектура и ПО

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| Резкий переход к микросервисам | Много сетевых вызовов вместо локальных операций | Рост latency, сложность диагностики |
| Неправильные границы сервисов | Разделение по UI, а не по доменам данных | Чрезмерная связанность и распределённый монолит |
| Нет стратегии транзакций | Запись, оплата, уведомления и 1С требуют согласованности | Двойная запись, потерянные события, ручные исправления |
| API Gateway/Policy Engine в критическом пути | Все запросы проходят через контроль доступа | Gateway/OPA могут стать bottleneck без кэша и HA |

### 4.5. Процессы

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| Ручные процессы не описаны | Нельзя корректно автоматизировать неизвестный процесс | Автоматизация закрепит ошибки As-Is |
| Двойной учёт в Excel и 1С | Два источника истины | Расхождения при миграции и сверке |
| Нет регламента cutover/rollback | Непонятно, как переключаться на новую систему | Долгий простой при ошибке миграции |
| Нет политики качества данных | Дубли и неполные анкеты попадут в CRM | Ошибки в ЛК, уведомлениях, аналитике |

### 4.6. Персонал

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| IT-команда всего 3 человека | Слишком много новых компетенций одновременно | Узкое место в DevOps, безопасности, поддержке |
| Администратор сети выполняет всё | Bus factor = 1 | Зависимость от одного специалиста |
| Сотрудники привыкли к Excel | Сопротивление изменениям | Обход новой системы через старые файлы |
| Нет выделенного DPO/ИБ-роли | Privacy и аудит требуют постоянного владельца | Контроли останутся формальными |

### 4.7. Безопасность

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| RBAC/ABAC добавляется впервые | Права доступа влияют на каждый запрос | Ошибки прав блокируют пользователей или открывают лишние данные |
| Шифрование и KMS в критическом пути | Decrypt/encrypt требует задержек и ротации ключей | Замедление операций с медкартами |
| DLP/аудит могут генерировать много событий | Рост объёма логов и false positive | Перегрузка SIEM и команды |
| Требования 152-ФЗ влияют на архитектуру | Нельзя просто скопировать данные в облако/BI | Ограничения на миграцию и хранение |

### 4.8. Наблюдаемость и эксплуатация

| Проблема | Почему это узкое место | Последствие |
|----------|------------------------|-------------|
| Нет текущих baseline-метрик | Не с чем сравнивать новую систему | Нельзя доказать улучшение/деградацию |
| Нет end-to-end tracing | В микросервисах сложно найти медленный участок | Долгое расследование инцидентов |
| Нет SLO/SLA по процессам | Не определено, что считается нормой | Приоритизация инцидентов субъективна |
| Нет нагрузочного тестирования | x5 рост не проверен до запуска | Производственные сбои после релиза |

## 5. Рекомендации и приоритеты

| Приоритет | Мера | Что устраняет | Ответственный контур |
|-----------|------|---------------|----------------------|
| **P0** | Провести инвентаризацию данных, файлов, Excel и 1С-объектов | Риск неуправляемой миграции и потери данных | Архитектура + бизнес-аналитик |
| **P0** | Определить целевые домены и источники истины: Patient, Appointment, Medical Record, Billing, Lab Result | Дубли и распределённый монолит | Архитектор |
| **P0** | Сделать нагрузочную модель под x5 рост: RPS, IOPS, объём файлов, ETL-окна | Непредсказуемая производительность | Архитектор + DevOps |
| **P0** | Спроектировать cutover/rollback: pilot, parallel run, read-only freeze, сверки | Долгий простой при переключении | Project/IT |
| **P1** | Перевести 1С в более управляемый интеграционный контур: API/очередь/адаптер, где возможно клиент-серверный режим | Блокировки и задержки legacy | 1С + архитектура |
| **P1** | Ввести event bus/очередь для платежей, уведомлений и лаборатории | Потери событий, слабая связность | Backend |
| **P1** | Внедрить observability до миграции: метрики, tracing, audit, business KPIs | Слепая эксплуатация | DevOps |
| **P1** | Провести data cleansing: дедупликация пациентов, нормализация телефонов/e-mail, связывание файлов с patient_id | Ошибки CRM/ЛК/уведомлений | Data team |
| **P1** | Выделить защищённое объектное хранилище для PDF/JPG и запретить прямую работу с общим диском | Медленные файлы и утечки | IT + ИБ |
| **P2** | Обучить персонал и ввести регламенты работы без Excel-дублей | Обход новой системы | Бизнес + IT |
| **P2** | Создать DPO/ИБ-роль или внешнюю функцию контроля | Несоблюдение privacy-требований | Руководство |
| **P2** | Настроить autoscaling, capacity planning и регулярные performance tests | Деградация при росте филиалов | DevOps |

## 6. Рекомендуемый план миграции

1. **Discovery и baseline**: собрать текущие объёмы, частоту операций, размер файлов, список Excel/1С-объектов, текущие ручные процессы.
2. **Domain design**: определить границы доменов и источники истины, чтобы не строить распределённый монолит.
3. **Pilot migration**: перенести ограниченный набор пациентов/журналов в CRM и сервис записи, оставить 1С и старые файлы read-only для сверки.
4. **Parallel run**: временно вести процессы в новой системе и сверять с As-Is, но запретить новые Excel-дубли после стабилизации.
5. **Incremental cutover**: переводить процессы по доменам: запись → пациенты → медкарты → платежи → лаборатория → аналитика.
6. **Performance gates**: перед каждым этапом запускать нагрузочные тесты, проверку latency, отказоустойчивости, восстановления и деградации зависимостей.
7. **Decommission legacy**: после сверки и архивирования отключить старые Excel/папки как рабочий инструмент.

## 7. Критерии готовности к переходу

| Критерий | Минимальное значение |
|----------|----------------------|
| Успешная миграция тестовой выборки | Не менее 99% записей сопоставлены с patient_id |
| Ошибки дублей пациентов | Есть регламент ручной сверки и merge |
| Нагрузочный тест записи | Выдерживает x5 от текущей оценки с запасом 30% |
| Время ответа ключевых API | P95 не выше согласованного SLO |
| Отказ лаборатории/1С | Система сохраняет события в очереди и повторяет отправку |
| Rollback | Проверен на тестовом окружении |
| Observability | Есть dashboard по записи, платежам, лаборатории, ошибкам API |
| Безопасность | Нет критичных findings по доступу к PII/medical data |
