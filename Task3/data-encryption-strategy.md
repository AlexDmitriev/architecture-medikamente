# Стратегия защиты данных: Encryption at Rest and In Transit

## 1. Цель

Цель стратегии — определить, какие данные компании «Медикаменте» должны быть защищены при хранении и передаче, какие механизмы шифрования и контроля нужны в целевой архитектуре, а также какие программные и аппаратные средства следует использовать.

Стратегия учитывает:

- требования 152-ФЗ к персональным данным и специальным категориям ПДн;
- медицинские данные пациентов как наиболее чувствительный класс;
- финансовые, кадровые и договорные данные;
- будущие сервисы: портал пациента, портал ресепшена, CRM, МИС, платёжный шлюз, лабораторное API, аналитический слой BI/ML;
- принципы Privacy by Design, Data Minimization и Data Lineage.

## 2. Состояния данных

| Состояние | Описание | Примеры в «Медикаменте» | Основные риски | Базовая защита |
|-----------|----------|--------------------------|----------------|----------------|
| **At Rest** | Данные хранятся на диске, в БД, файловом хранилище, бэкапах | Excel, PDF/JPG, PostgreSQL, 1С, ClickHouse, S3/MinIO, бэкапы | Кража носителя, доступ к файловой системе, утечка бэкапа | AES-256, TDE/pgcrypto, SSE-KMS, BitLocker/LUKS, шифрование бэкапов |
| **In Transit** | Данные передаются между пользователями, сервисами и внешними системами | Web/mobile → API, API → БД, МИС → лаборатория, платёжный шлюз → ККМ/1С | Перехват, MITM, подмена сервиса, утечка через API | TLS 1.3, mTLS, VPN/IPsec, HSTS, certificate pinning для mobile |
| **In Use** | Данные обрабатываются приложениями, ETL, аналитикой | МИС, CRM, Jupyter, ETL, BI/ML pipeline | Выгрузки, логи, дампы памяти, notebook leakage | Маскирование, токенизация, псевдонимизация, запрет PII в логах, RBAC/ABAC |

## 3. Классификация по чувствительности и риску

| Класс | Уровень чувствительности | Профиль риска | Примеры | Требования к защите |
|-------|--------------------------|---------------|---------|---------------------|
| **C1 Public** | Низкий | Репутационный | Общая информация об услугах, публичное расписание без ПДн | TLS для сайта, контроль целостности |
| **C2 Internal** | Средний | Операционный | Внутренние регламенты, агрегированные отчёты без ПДн | Шифрование дисков, RBAC, TLS |
| **C3 PII** | Высокий | Правовой и репутационный | ФИО, дата рождения, телефон, e-mail, адрес | AES-256 at rest, TLS/mTLS, маскирование, аудит |
| **C4 Sensitive Medical PII** | Критический | Правовой, медицинская тайна, репутационный | Диагнозы, хронические заболевания, анализы, заключения | Отдельный домен, AES-256 + KMS, mTLS, ABAC, MFA, полный аудит |
| **C5 Financial** | Высокий | Финансовый и регуляторный | Суммы оплат, чеки, договоры, данные эквайринга | Токенизация, TLS/mTLS, PCI DSS-подход, аудит |
| **C6 HR** | Высокий | Правовой и трудовой | Паспортные данные сотрудников, СНИЛС, ИНН, зарплата | Отдельный HR-контур, AES-256, RBAC, аудит |
| **C7 Secrets** | Критический | Компрометация всей системы | Пароли, API-ключи, ключи шифрования, TLS private keys | Vault/HSM, ротация, запрет хранения в коде, MFA/PAM |
| **C8 Metadata** | Средний/Высокий | Повторная идентификация | Имена файлов `ФИО-ДР`, audit trail, IP, user-agent | Минимизация, псевдонимизация, контроль доступа |

## 4. Матрица «Данные — необходимость защиты — инструменты»

| Данные | Состояние | Класс | В чём необходимость защиты | Инструменты защиты |
|--------|-----------|-------|-----------------------------|--------------------|
| ФИО, дата рождения пациента | At Rest / In Transit / In Use | C3 PII | Идентифицируют субъекта ПДн; используются почти во всех процессах | PostgreSQL TDE/pgcrypto или field-level AES-256, TLS 1.3, маскирование в UI/логах, patient UUID вместо ФИО в файлах |
| Телефон, e-mail | At Rest / In Transit / In Use | C3 PII | Каналы связи с пациентом, риск фишинга и спама при утечке | AES-256, TLS 1.3, маскирование `+7***1234`, DLP для почты, запрет записи в debug-логи |
| Адрес, место работы/учёбы | At Rest / In Use | C3 PII | Избыточные данные повышают ущерб при утечке; нужны не во всех процессах | Data Minimization, шифрование, ограничение доступа по цели обработки, удаление из аналитических витрин |
| Диагнозы, жалобы, хронические заболевания | At Rest / In Transit / In Use | C4 Sensitive Medical PII | Специальная категория ПДн; утечка создаёт максимальный правовой и репутационный риск | Отдельный medical domain, AES-256 field-level encryption, ключи в Vault/HSM, ABAC «врач → свои пациенты», MFA, полный immutable audit |
| Результаты анализов | At Rest / In Transit / In Use | C4 Sensitive Medical PII | Медицинская тайна; при API-интеграции возможен BOLA/IDOR | mTLS с лабораторией, API Gateway, OPA-политики, подпись сообщений, шифрование в хранилище, аудит просмотра |
| Медицинские файлы PDF/JPG | At Rest / In Transit | C4 Sensitive Medical PII | Неструктурированные файлы легко копируются, отправляются и индексируются | S3/MinIO SSE-KMS, запрет общего диска, DLP, pre-signed URLs с TTL, антивирус и content scanning |
| Записи на приём | At Rest / In Transit | C3 PII | Связывают пациента с врачом и медицинской услугой | TLS, шифрование БД, ABAC по филиалу/врачу, псевдонимизация ФИО в расписании |
| Договоры и согласия | At Rest / In Transit | C3/C5 | Доказывают законность обработки и условия услуги; содержат ПДн | Электронное хранилище документов с SSE-KMS, ЭП/хеш целостности, retention policy, аудит доступа |
| Финансовые операции, чеки, суммы оплат | At Rest / In Transit | C5 Financial | Утечка раскрывает платежи и услуги пациента; двойной учёт в Excel создаёт неконтролируемые копии | Платёжный шлюз, TLS/mTLS, токенизация платёжных реквизитов, отказ от Excel-дублей, шифрование 1С/БД |
| Кадровые данные сотрудников | At Rest / In Transit | C6 HR | ПДн сотрудников, зарплата и налоговые данные | Отдельные роли HR/бухгалтерия, AES-256, TLS, аудит выгрузок, DLP |
| Учётные записи, пароли, API-ключи | At Rest / In Transit / In Use | C7 Secrets | Компрометация секретов ведёт к компрометации всех классов данных | HashiCorp Vault / HSM, bcrypt/argon2 для паролей, mTLS private keys в Vault, ротация, запрет секретов в Git |
| Метаданные файлов и идентификаторы | At Rest / In Use | C8 Metadata | ФИО/дата рождения в имени файла раскрывают ПДн даже без открытия документа | `patient-{uuid}`, запрет PII в путях, DLP/сканер имён файлов, каталог данных |
| Логи приложений и аудита | At Rest / In Transit | C8 Metadata + C3/C4 при ошибках | Логи могут случайно содержать PII/медицинские данные | Маскирование, structured logging allowlist, TLS до Elastic, WORM/immutable storage для audit log |
| Данные BI/ML | At Rest / In Use | C2/C3/C4 до обезличивания | Аналитика на сырых Excel создаёт риск массовой утечки | Data Lake raw zone с шифрованием, anonymization pipeline, ClickHouse только для anonymized/aggregated views, запрет прямого доступа аналитиков к raw PII |
| Бэкапы | At Rest / In Transit | Наследуют максимальный класс исходных данных | Один бэкап может содержать полный массив ПДн и медицинских данных | Шифрование бэкапов AES-256, KMS, offline/immutable copies, регулярная проверка восстановления, контроль доступа |

## 5. Инструменты защиты At Rest

| Зона | Инструмент | Что защищает | Требования к внедрению |
|------|------------|--------------|------------------------|
| Операционные БД | PostgreSQL TDE/pgcrypto, field-level encryption | CRM, МИС, записи, согласия | Ключи только через KMS/Vault; отдельные ключи для `pii.sensitive` |
| Файловое хранилище | MinIO/S3 SSE-KMS, object lock | PDF/JPG, договоры, заключения | Запрет общего SMB для медицинских файлов; доступ через API |
| Legacy-период | BitLocker/LUKS | Windows/Linux серверы, временные файловые зоны | Использовать как переходную меру, не как единственный контроль |
| 1С | Шифрование томов + сегментация + права 1С | Бухгалтерия, склад, HR | Перевести из файлового режима в клиент-серверный, где возможно |
| Секреты | HashiCorp Vault, HSM/TPM | API-ключи, TLS private keys, master keys | Ротация, MFA для админов, audit device Vault |
| Бэкапы | Backup encryption + immutable storage | Все резервные копии | Отдельные ключи, запрет хранения ключей рядом с бэкапами |
| Аналитика | Encrypted Data Lake Raw Zone | Сырые данные до обезличивания | Доступ только ETL-сервисам; запрет доступа бизнес-аналитиков |

## 6. Инструменты защиты In Transit

| Поток | Риск | Механизм защиты |
|-------|------|-----------------|
| Пациент → портал / mobile app | Перехват учётных данных и ПДн | HTTPS TLS 1.3, HSTS, secure cookies, certificate pinning для mobile |
| Сотрудник → внутренний портал | Перехват сессии, доступ из небезопасной сети | TLS 1.3, SSO/OIDC, MFA, VPN/ZTNA для административных функций |
| Privacy API Gateway → микросервисы | MITM внутри сети, lateral movement | mTLS service-to-service, короткоживущие сертификаты, service mesh |
| МИС → лаборатория | Подмена лаборатории, утечка результатов анализов | mTLS, подпись payload, allowlist IP/сертификатов, OPA-проверка patient_id |
| Платёжный шлюз → ККМ/эквайринг/1С | Подмена платежа, утечка финансовых данных | TLS/mTLS, токенизация, минимизация передаваемых полей |
| ETL → Data Lake / ClickHouse | Утечка при выгрузке больших массивов | TLS/mTLS, временные credentials, контроль lineage, checksum |
| Приложения → Elastic / мониторинг | PII в логах, перехват логов | TLS, маскирование до отправки, allowlist полей, отдельный контур audit log |
| Администраторы → Vault/KMS | Компрометация ключей | MFA, PAM, TLS, запрет прямого shell-доступа, audit log |

## 7. Управление ключами

| Правило | Решение |
|---------|---------|
| Ключи не хранятся в коде и конфигурациях приложений | Использовать Vault/KMS, доступ по workload identity |
| Разные классы данных используют разные ключи | Отдельные ключи для `pii`, `pii.sensitive`, `fin`, `hr`, backup |
| Доступ к ключу не равен доступу к данным | Приложение получает decrypt только после OPA/ABAC проверки |
| Ключи регулярно ротируются | Плановая ротация: C4/C7 — 90 дней, C3/C5/C6 — 180 дней, бэкапы — по политике |
| Компрометация ключа должна обнаруживаться | Vault audit device, SIEM-алерты на массовый decrypt |
| Удаление данных должно быть возможно | Crypto-shredding для объектов с индивидуальными data encryption keys |

## 8. Автоматизированный контроль

| Контроль | Инструмент | Что проверяет | Реакция |
|----------|------------|---------------|---------|
| Сканирование хранилищ на PII | Microsoft Purview / OpenMetadata scanner | Excel, PDF/JPG, БД, data lake | Присвоить тег, отправить в remediation queue |
| Проверка API-контрактов | OpenAPI linter + OPA Conftest | Нет ли `pii.sensitive` в публичных ответах без политики | Блокировать merge/release |
| Поиск секретов в коде | Gitleaks / TruffleHog | API-ключи, private keys, пароли | Блокировать commit/CI |
| Проверка TLS | SSL Labs / testssl.sh / cert-manager metrics | Версии TLS, срок сертификатов, слабые cipher suites | Алерт и запрет деплоя |
| Контроль шифрования Kubernetes | OPA Gatekeeper / Kyverno | Secrets encrypted at rest, запрет plaintext env | Блокировать apply |
| Контроль логов | Semgrep + log pipeline filters | PII/medical data в логах | Блокировать релиз или маскировать |
| Контроль доступа | OPA decision logs + SIEM | Нетипичный доступ врача/сотрудника к данным | Алерт, временная блокировка, расследование |
| Контроль бэкапов | Backup audit + restore drills | Бэкапы зашифрованы, восстановимы, ключи доступны | Инцидент при незашифрованном бэкапе |
| Контроль аналитики | OpenMetadata lineage + policy tags | В BI не попали raw `pii`/`pii.sensitive` | Блокировать публикацию витрины |

## 9. Минимальный набор базовых инструментов

Для первого этапа внедрения достаточно следующего набора:

1. **TLS 1.3 на всех пользовательских и сервисных API**.
2. **mTLS для внутренних сервисов и API лаборатории**.
3. **Vault/KMS для ключей шифрования и секретов**.
4. **Шифрование операционных БД и файлового хранилища**.
5. **OpenMetadata/Purview для классификации и тегирования данных**.
6. **OPA для ABAC/RBAC и запрета доступа к чужим данным**.
7. **Elastic/SIEM для аудита доступа и алертов**.
8. **Gitleaks/Semgrep/OPA Conftest в CI/CD**.
9. **DLP для почты, файлового хранилища и рабочих станций**.
10. **Шифрование бэкапов и регулярная проверка восстановления**.

## 10. Приоритеты внедрения

| Приоритет | Что сделать | Обоснование |
|-----------|-------------|-------------|
| P0 | Убрать PII из имён файлов/папок, включить шифрование файлового сервера и бэкапов | Быстро снижает риск утечки As-Is |
| P0 | Внедрить TLS/mTLS для API и интеграции лаборатории | Защищает наиболее чувствительный новый поток |
| P0 | Ввести Vault/KMS и запрет секретов в коде | Без KMS невозможно безопасно управлять шифрованием |
| P1 | Перенести медицинские карты из общего диска в защищённое объектное хранилище | Убирает неконтролируемое копирование PDF/JPG |
| P1 | Внедрить OPA/ABAC и аудит доступа | Предотвращает доступ сотрудников к чужим данным |
| P1 | Включить DLP и сканирование PII | Помогает найти уже существующие неконтролируемые копии |
| P2 | Построить privacy-preserving analytics layer | BI/ML без прямого доступа к ПДн |
| P2 | Перевести 1С из файлового режима и сегментировать legacy-контур | Снижает blast radius компрометации |
