# Cutover-план миграции на новую платформу

## 1. Выбранная стратегия

Для миграции «Медикаменте» выбрана стратегия **Parallel run** — параллельный запуск старой и новой системы с постепенным переводом нагрузки.

### Почему не High-level design

High-level design полезен как подготовительный архитектурный этап: он помогает определить домены, границы модулей и целевую архитектуру. Но сам по себе он не является безопасной cutover-стратегией для перехода с рабочих Excel/1С/сканов на новую систему. Он не отвечает на вопросы синхронизации, сверки данных, отката и работы пользователей в переходный период.

### Почему не Branch by abstraction

Branch by abstraction хорошо подходит, когда уже есть единая кодовая база или монолит, внутри которого можно постепенно подменять реализации за абстрактным слоем. В текущем случае «монолит» фактически состоит из Excel, сканов, файлового сервера, 1С и ручных операций. Единого приложения, куда можно внедрить слой абстракции, нет. Для отдельных интеграций, например 1С или ККМ, этот подход можно использовать локально, но не как основную стратегию всей миграции.

### Почему Parallel run подходит лучше

Parallel run позволяет:

- запустить новую CRM, сервис записи и портал рядом со старыми Excel-журналами;
- сравнивать записи, пациентов, платежи и результаты анализов между старым и новым контуром;
- постепенно переводить пользователей и процессы без резкого простоя;
- сохранить возможность отката на старые Excel/1С-процессы до подтверждения качества данных;
- снизить риски для медицинских процессов, где ошибка миграции может повлиять на пациента.

Основное ограничение стратегии — временная сложность: нужно синхронизировать данные между двумя контурами, контролировать двойной ввод и ежедневно сверять расхождения.

## 2. Область миграции

| Область | As-Is | To-Be | Способ перевода |
|---------|-------|-------|-----------------|
| Запись на приём | Excel-журналы по врачам | Сервис записи + портал пациента + портал ресепшена | Parallel run, затем freeze Excel |
| Пациенты | Excel `Patients`, папки `Pacient-FIO-BD` | CRM / единый patient profile | Миграция пачками, дедупликация |
| Медицинские карты | PDF/JPG на общем диске | МИС + защищённое файловое хранилище | Постепенный перенос файлов с привязкой к `patient_id` |
| Платежи | ККМ + 1С + Excel-дубли | Платёжный шлюз + интеграция с 1С/ККМ | Пилот по ограниченному числу операций |
| Лаборатория | Excel-реестры | API-интеграция с лабораторией | Сначала read-only import, затем полноценный API |
| Аналитика | Jupyter по Excel | Data Lake + обезличивание + ClickHouse | После стабилизации операционных данных |

## 3. Участники и роли

| Роль | Ответственность |
|------|-----------------|
| **Технический директор / архитектор** | Владелец cutover-плана, архитектурные решения, go/no-go |
| **Администратор сети / DevOps** | Инфраструктура, бэкапы, мониторинг, доступы, rollback |
| **Бизнес-аналитик** | Инвентаризация Excel, правила сверки, отчёты расхождений |
| **Ресепшен** | Проверка записи пациентов, фиксация ошибок пользовательского сценария |
| **Врачи** | Проверка доступности медкарт, корректности расписания и результатов анализов |
| **Кассиры** | Проверка оплаты, чеков, статусов платежей |
| **Бухгалтерия** | Сверка 1С, платежей, возвратов, зарплатных/налоговых данных |
| **Склад** | Проверка ТМЦ и интеграции с 1С Торговля |
| **ИБ / DPO-функция** | Контроль доступа к ПДн, аудит, согласия, требования 152-ФЗ |
| **Руководство** | Утверждение окна переключения, допустимого простоя и коммуникаций |

## 4. Cutover-план

| Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|------|-------------------|-----------------|---------------|-------------|--------------------------|
| 1. Инициация миграции | Утвердить стратегию Parallel run, границы миграции и критерии успеха | Назначить владельца миграции; утвердить scope: запись, пациенты, медкарты, платежи, лаборатория; определить SLO и допустимый простой | Технический директор, руководство, бизнес-аналитик | Неделя 1 | Риск: размытый scope. Мера: зафиксировать список процессов и критерии go/no-go в документе |
| 2. Инвентаризация As-Is | Собрать полный перечень Excel, сканов, папок, 1С-объектов и ручных операций | Описать источники данных; посчитать объёмы; найти дубли; определить владельцев данных; зафиксировать текущие бизнес-метрики | Бизнес-аналитик, ресепшен, бухгалтерия, администратор сети | Недели 1–2 | Риск: часть файлов не найдена. Мера: скан файлового сервера, интервью с отделами, контрольный список источников |
| 3. Проектирование доменов | Определить целевые сущности и источники истины | Patient, Appointment, MedicalRecord, Payment, LabResult, Contract; определить ключи сопоставления; описать правила дедупликации | Технический директор, бизнес-аналитик | Неделя 2 | Риск: распределённый монолит и дубли. Мера: один источник истины на домен, ADR по границам сервисов |
| 4. Подготовка инфраструктуры | Развернуть тестовый и пилотный контур новой платформы | Kubernetes/серверы; БД; хранилище файлов; API Gateway; мониторинг; бэкапы; тестовые доступы | Администратор сети, технический директор | Недели 2–4 | Риск: нехватка ресурсов. Мера: capacity plan под x5 рост, нагрузочный тест до пилота |
| 5. Подготовка безопасности | Включить базовые контроли до загрузки реальных ПДн | RBAC/ABAC; шифрование at rest; TLS/mTLS; аудит доступа; маскирование логов; роли для врачей/ресепшена/кассиров | ИБ/DPO, администратор сети, технический директор | Недели 3–4 | Риск: ПДн попадут в тестовый контур без защиты. Мера: запрет production data до прохождения security checklist |
| 6. Очистка данных | Подготовить данные к миграции | Нормализовать телефоны/e-mail; удалить явные дубли; связать папки пациентов с `patient_id`; подготовить mapping Excel → CRM/МИС | Бизнес-аналитик, ресепшен, врачи | Недели 3–5 | Риск: неверное сопоставление пациента и медкарты. Мера: ручная сверка критичных записей и журнал исключений |
| 7. Тестовая миграция | Перенести ограниченную тестовую выборку | 20–50 пациентов; несколько врачебных журналов; тестовые платежи; тестовые результаты анализов; проверить отчёты расхождений | Бизнес-аналитик, администратор сети, пользователи-валидаторы | Неделя 5 | Риск: потеря данных или неверный формат. Мера: миграция только из копии, checksum, reconciliation report |
| 8. Функциональное тестирование | Проверить ключевые пользовательские сценарии | Пациент записывается; ресепшен видит запись; врач видит свой журнал; кассир принимает оплату; бухгалтер видит проводку; лабораторный результат привязан к пациенту | Ресепшен, врач, кассир, бухгалтер, бизнес-аналитик | Неделя 6 | Риск: сценарии работают технически, но неудобны бизнесу. Мера: UAT с реальными ролями и фиксацией замечаний |
| 9. Нагрузочное тестирование | Проверить систему под ожидаемый рост | Тест x5 текущей нагрузки + 30% запас; проверить запись, поиск пациента, загрузку файлов, API лаборатории, платежи | Администратор сети, технический директор | Неделя 6 | Риск: деградация в пиковые часы. Мера: performance gate; оптимизация БД/кэша/очередей до пилота |
| 10. Подготовка parallel run | Настроить параллельную работу старого и нового контура | Определить, что вводится в новой системе, что сверяется со старой; настроить ежедневные отчёты расхождений; обучить пользователей | Технический директор, бизнес-аналитик, руководители отделов | Неделя 7 | Риск: хаотичный двойной ввод. Мера: регламент «где первичный ввод», ответственные за сверку, журнал расхождений |
| 11. Pilot parallel run | Запустить новую систему на ограниченной группе | 1–2 врача, часть ресепшена, ограниченный набор пациентов; старые Excel остаются как контрольный контур | Ресепшен, врачи пилота, бизнес-аналитик, IT | Недели 8–9 | Риск: пользователи возвращаются в Excel. Мера: ежедневный контроль, обучение на месте, быстрые исправления UX |
| 12. Ежедневная сверка | Сравнивать новый и старый контур | Записи на приём; новые пациенты; изменения контактов; оплаты; лабораторные результаты; список расхождений и root cause | Бизнес-аналитик, ресепшен, бухгалтерия | Ежедневно во время pilot run | Риск: расхождения накапливаются. Мера: SLA на разбор расхождений в течение 1 рабочего дня |
| 13. Расширение pilot scope | Постепенно подключить всех врачей и ресепшен | Расширить сервис записи; подключить больше пациентов; перевести новые записи в новый сервис как primary | Технический директор, руководители отделов | Недели 10–11 | Риск: нагрузка на поддержку. Мера: выделить горячую линию и окно стабилизации |
| 14. Freeze старых журналов | Перевести Excel-журналы в режим read-only | Новые записи создаются только в сервисе записи; Excel доступен только для просмотра и сверки | Технический директор, администратор сети, ресепшен | Конец недели 11 | Риск: сотрудники продолжают делать копии Excel. Мера: права read-only, DLP/аудит файлового сервера, приказ/регламент |
| 15. Cutover записи и пациентов | Сделать CRM и сервис записи основным контуром | Переключить порталы; включить уведомления; обновить инструкции; проверить мониторинг и алерты | Технический директор, ресепшен, DevOps | Неделя 12, низкая нагрузка / выходные | Риск: недоступность записи. Мера: rollback на Excel read-only копию + ручной журнал аварийной записи |
| 16. Cutover платежей | Перевести оплату через платёжный шлюз с интеграцией в 1С/ККМ | Проверить фискализацию; статусы оплаты; возвраты; сверку с 1С; отключить Excel-дубли кассиров | Кассиры, бухгалтерия, технический директор | Недели 13–14 | Риск: двойное списание или потеря платежа. Мера: идемпотентные payment_id, очередь событий, ежедневная сверка 1С |
| 17. Cutover лаборатории | Перевести лабораторные результаты с Excel-реестров на API | Включить mTLS API; настроить retry; сверить результаты с ручным реестром; обеспечить привязку к `patient_id` | Врачи, лаборатория, технический директор | Недели 15–16 | Риск: дубли/потеря результатов. Мера: idempotency key, reconciliation report, временный read-only импорт Excel |
| 18. Cutover медкарт и файлов | Перенести медицинские файлы в защищённое хранилище | Перенос PDF/JPG; привязка к пациентам; проверка прав врачей; запрет записи новых файлов на общий диск | Врачи, администратор сети, ИБ/DPO | Недели 16–18 | Риск: врач не видит нужный документ. Мера: быстрый fallback к read-only архиву, журнал отсутствующих файлов |
| 19. Аналитический слой | Запустить BI/ML на обезличенных данных | ETL в Data Lake; обезличивание; ClickHouse-витрины; запрет доступа аналитика к raw PII | Бизнес-аналитик, технический директор, ИБ/DPO | После стабилизации операционных доменов | Риск: PII попадёт в BI. Мера: OpenMetadata tags, policy gate на публикацию витрин |
| 20. Финальная стабилизация | Подтвердить, что новая система работает как primary | Проверить SLO; закрыть критичные дефекты; провести обучение; обновить регламенты; подготовить отчёт go-live | Все владельцы процессов | 2–4 недели после cutover | Риск: скрытые дефекты проявятся позже. Мера: усиленный мониторинг, ежедневный standup, backlog стабилизации |
| 21. Decommission legacy | Вывести старые Excel/папки из операционной работы | Архивировать старые данные; сохранить read-only архив; отключить права записи; описать порядок доступа к архиву | Технический директор, администратор сети, ИБ/DPO | Через 1–2 месяца стабильной работы | Риск: преждевременное отключение legacy. Мера: отключать только после успешной сверки и подписания владельцами процессов |

## 5. Критические моменты cutover

| Критический момент | Почему важен | Контроль |
|--------------------|--------------|----------|
| Первая загрузка реальных ПДн в новую систему | Ошибка может привести к утечке или потере данных | Security checklist, шифрование, аудит, доступ только по ролям |
| Freeze Excel-журналов | После этого старая система перестаёт быть primary | Read-only права, резервная копия, аварийный бумажный/Excel-журнал |
| Переключение записи пациентов | Влияет на ресепшен, врачей и пациентов | Низкая нагрузка, горячая линия, мониторинг API |
| Переключение платежей | Ошибка напрямую влияет на деньги и 1С | Идемпотентность, сверка с ККМ/1С, тест возвратов |
| Переключение лаборатории | Ошибка влияет на медицинские решения | Сверка реестров, retry, ручной fallback |
| Закрытие старого общего диска на запись | Убирает неуправляемые копии, но может сломать привычные процессы | Обучение, read-only архив, контроль обращений |

## 6. План отката

| Сценарий проблемы | Условие отката | Действия | Ответственные |
|-------------------|----------------|----------|---------------|
| Новая запись недоступна | P1-инцидент более 30 минут или потеря записей | Переключить ресепшен на аварийный журнал; отключить публичную самозапись; после восстановления импортировать аварийные записи | Технический директор, ресепшен, администратор сети |
| Ошибки миграции пациентов | Более 1% записей не сопоставлены или найдены критичные ошибки | Остановить расширение pilot scope; вернуть процесс к старому журналу; исправить mapping и повторить миграцию | Бизнес-аналитик, технический директор |
| Платежи не проходят или дублируются | Есть двойное списание, потерянный чек или несверка с 1С | Остановить новый платёжный контур; вернуться к ККМ/1С As-Is; провести ручную сверку | Кассиры, бухгалтерия, технический директор |
| API лаборатории возвращает некорректные данные | Потеря/дубли результатов или неверный `patient_id` | Отключить автоматическую загрузку; вернуться к read-only Excel-реестру; включить ручную валидацию | Врачи, лаборатория, технический директор |
| Нарушение доступа к ПДн | Пользователь видит чужие данные | Немедленно остановить affected endpoint; отозвать сессии; включить read-only режим; расследовать audit log | ИБ/DPO, технический директор |
| Производительность ниже SLO | P95 превышает SLO более 2 часов в рабочее время | Откатить трафик на старый процесс для затронутого домена; провести performance fix | Администратор сети, технический директор |

## 7. Управление рисками Parallel run

| Риск | Вероятность | Влияние | Меры снижения | Триггер эскалации |
|------|-------------|---------|---------------|-------------------|
| Расхождение данных между старым и новым контуром | Высокая | Высокое | Ежедневная сверка, reconciliation reports, владелец каждого расхождения | Расхождение не закрыто больше 1 рабочего дня |
| Двойной ввод создаёт ошибки | Средняя | Высокое | Чётко определить primary-систему на каждом этапе, инструкции пользователям | Более 5 ошибок ввода в день |
| Пользователи продолжают работать в Excel | Высокая | Среднее | Read-only freeze, обучение, контроль файлового сервера | Новые Excel-копии после freeze |
| Новая система не выдерживает нагрузку | Средняя | Высокое | Нагрузочные тесты, performance gates, мониторинг | P95 выше SLO или error rate выше порога |
| Ошибка прав доступа | Средняя | Критическое | ABAC/RBAC тесты, UAT по ролям, аудит | Любой подтверждённый доступ к чужим данным |
| Некорректная интеграция с 1С/ККМ | Средняя | Высокое | Идемпотентность, очередь событий, сверка с 1С | Несверка платежей за день |
| Потеря доверия пользователей | Средняя | Среднее | Обучение, поддержка на месте, быстрый feedback loop | Рост обращений и ручных обходов |

## 8. Go/No-Go критерии

| Область | Go-критерий |
|---------|-------------|
| Данные | Не менее 99% записей пилотной выборки сопоставлены с `patient_id`; критичные ошибки отсутствуют |
| Запись | Пациент может записаться, ресепшен видит запись, врач видит слот; P95 API в пределах SLO |
| Платежи | Тестовые и пилотные платежи сверяются с ККМ и 1С; возврат протестирован |
| Лаборатория | Результаты анализов приходят с корректным `patient_id`; дубли подавляются |
| Безопасность | Нет критичных замечаний по доступу к ПДн/медицинским данным |
| Наблюдаемость | Есть dashboards и алерты по записи, платежам, лаборатории, ошибкам API |
| Откат | Rollback-процедуры проверены на тестовой среде |
| Пользователи | Ресепшен, врачи, кассиры и бухгалтерия прошли UAT и подписали готовность |

## 9. Коммуникационный план

| Аудитория | Сообщение | Канал | Когда |
|-----------|-----------|-------|-------|
| Руководство | Статус готовности, риски, go/no-go | Еженедельный отчёт | Каждую неделю до cutover |
| Ресепшен | Как вести запись, куда вносить первичные данные, как сообщать об ошибках | Очное обучение + инструкция | За 1 неделю до pilot |
| Врачи | Как смотреть расписание, медкарты и анализы | Обучение + быстрый справочник | За 1 неделю до подключения врача |
| Кассиры и бухгалтерия | Как сверять платежи, что делать при ошибке | Регламент + контакт поддержки | До cutover платежей |
| Пациенты | Информация о запуске ЛК/самозаписи | Сайт, SMS/e-mail | Перед публичным запуском |
| IT/поддержка | Runbook, контакты, thresholds, rollback | Внутренний канал + runbook | До начала pilot |
